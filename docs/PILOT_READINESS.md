### Current security and deployment contracts

The supported reset API is **`POST /api/auth/reset-password` with JSON `{token,password}`**. The obsolete path-token route has no consumer and is removed. This supersedes the historical compatibility route in the original B36.1A design/plan. Nginx rejects case-insensitive and normalized legacy descendants without credential-bearing access/error logs; body reset strips query parameters and does not log its request URL. Behavioral Docker regressions exercise lowercase, uppercase, mixed and encoded variants and synthetic-credential absence from logs.

Registration and reset consume fragment credentials in memory, immediately remove the URL fragment and handle a new fragment while the same page remains mounted. No invitation/reset token is stored in localStorage, sessionStorage or IndexedDB. Admin-defined community/unit/owner-or-tenant claims remain server authoritative.

Registration and Reset invalidate superseded requests on credential replacement/unmount. Deferred component and browser checks prove an old success/error cannot change session, navigation, messages or the newer request's loading state. This suppresses obsolete client effects, not already-started server transactions. Temporary response mocks were removed; running Nginx configuration was compared with the repository and matched exactly. The log regression now waits for the actual synthetic upstream through the proxy with a bounded, credential-free readiness probe.

Git checkout now preserves LF for shell scripts and SQL migrations. A fresh Windows `core.autocrlf=true` checkout is tested. No migration/checksum algorithm or stored history was rewritten: all26 applied checksums inspected during diagnosis matched committed LF bytes and none matched the accidental CRLF checkout. The rebuilt backend subsequently accepted all31 then-current migrations.

## Safe provision and inspection for a fresh pilot

Keep `SEED_DB: 'false'`. Do not run `src/backend/seed.js`: it is a destructive demo initializer, not a pilot provisioning command. There is currently no packaged administrator/community bootstrap command or create-community API. Initial provision is a controlled operation by the trusted database operator against the explicitly identified pilot database, using the current schema and models. Record the non-secret row IDs and relationships before making the pilot available.

Create a fresh community and administrator with a unique email and a securely generated password hashed with the existing bcrypt authentication mechanism (`User.create` takes `password_hash`, never plaintext). Establish the real complex/community relationship and `admin_complexes` membership for that administrator; do not reuse seeded identities or infer access from a display name. Preserve the deployed authentication/invitation secrets and trusted `PUBLIC_APP_URL`. Routine deployment must reuse runtime configuration; a missing local `.env` is not authorization to replace container secrets.

After the administrator can log in and sees the intended scope, use the existing Estructura UI and its authorized hierarchy operations to prepare buildings, floors and units under that complex. Complex creation has its own existing privileged route; do not grant extra roles to work around it. Invite residents through the administrator invitation workflow, selecting the actual community, unit and owner/tenant relation. Verify acceptance and active `unit_ownerships` against the same hierarchy. Ordinary onboarding does not use public self-registration or a seed password.

Before any legacy-demo or text-encoding cleanup, inspect exact primary keys, community/complex associations, dependencies and the actual stored values in the intended database. A word resembling “demo”, a familiar unit label or suspected mojibake does not establish ownership of a row. Record and review an explicit identity list and narrow predicates; leave unidentified historical data untouched. Never fuzzy-delete by name, remove an arbitrary whole community, truncate tables or rewrite applied migrations for cosmetic cleanup.

For disposable QA, generate a unique marker and fresh identities, keep credentials only in process memory, and record every created ID. Cleanup must first check both the exact IDs and their marker/parent relationships inside a transaction. Remove only the recorded reply/ticket, notification/audit, invitation, membership and hierarchy fixtures, in foreign-key order; assert affected counts before commit. If any identity, child row or count differs, roll back and inspect. Verify zero residue for the recorded IDs and exact marker afterward, alongside an unchanged unrelated-data baseline. Retain the exact run-specific predicates and counts in the QA report; this is not a reusable broad deletion script.

The named Docker upload volume `comunidad-app_upload_data`, mounted at `/app/uploads`, is protected persistent storage. Verify its actual mount before recreation. Remove only an explicitly recorded QA upload whose database association and filename match the fixture; never remove the volume, use `docker compose down -v`, or delete unknown files. Persistence is not a backup. Production backup/restore and trash features remain deferred.
